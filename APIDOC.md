## Module `smpapi` {#module-smpapi}

smpapi: the client half of SMP as a library, over a `Transport`.

Each command sends a request, waits for the response that has the request's sequence number and answers what the response holds
as a value, a `Result` whose error is an `SmpError`.  Nothing is printed and no file is touched, so a phone app, a tool on a PC
and a Central on a board call the same functions and differ only in the transport they hand over (smptransport.nv: the console
framing over a wire, the packets as they are over a pipe; smpscript.nv: a script for a test; a program's own implementation of
the trait for the GATT client of a phone or of the noble Host).

  let opt = smpapi.options(2000, 3)
  match smpapi.image_list(link, opt)
      Ok(slots) => ...
      Err(e)    => println(e.message())

A request that is not answered within the timeout of `CallOptions` is sent again, up to `tries` times in all.  A packet that is no
response (a header the protocol does not define, a length that is not the packet's, a body that is not a whole map) or whose
sequence number is another is passed over, and a request that got only such packets is `E_BAD_ANSWER` when one had its number
and `E_NO_ANSWER` when none had.  The commands of a group the server does not have come back as the server's code, `ENOTSUP`.

The buffer a request is built in, and its numbering, belong to the package: one request is in flight in a process at a time.
The size of a request is bounded by `smp_buf_bytes` of mcumgr-nv's configuration, 512 by default, and by the transport's `mtu`;
a response may be of any size the transport delivers.

## Module `smpbody` {#module-smpbody}

smpbody: a response packet read as bytes.

A response is the 8-byte header and a body, a CBOR map of text keys.  The server of mcumgr-nv writes flat maps, a Zephyr server
writes an array of maps under `images`, and any server may write keys after an array.  This module reads such a packet without
a buffer of the package's configuration, so the size of a response is the size the transport delivered, and it checks every
head against the end of the packet before it reads on: a packet cut anywhere is refused by `valid`, never read past its end.

`valid` is the one check.  The readers after it take a packet that passed it, and answer a fallback for a key that is absent or
of another type.

## Module `smpcli` {#module-smpcli}

smpcli: the commands of the `smp-client-nv` program.

  smp-client-nv --tcp HOST:PORT | --serial PATH [--baud N] | --dev PATH | --pipe PROGRAM
                [--timeout MS] [--tries N] COMMAND

  echo TEXT                 the server answers TEXT
  params                    the server's buffer size and count
  reset                     the server resets after it answers
  image list                the images the server holds
  image upload FILE [--image N]
                            sends a NOVB image or a package to the second slot; with --image 1 the
                            file `novofs-tools mk --target` wrote, to the data region
  image test HASH           marks the image with the hash (hex) for the next start
  image confirm [HASH]      confirms the image that runs, or makes the staged one permanent
  image erase               erases the second slot
  fs upload FILE NAME       sends FILE as the file NAME
  fs download NAME FILE     writes the file NAME to FILE
  fs status NAME            the length of the file NAME
  fs hash NAME              the CRC-32 of the file NAME
  fs close                  closes the files of a transfer that stalled
  pack IMAGE -o PACKAGE     wraps a NOVB image in the package of smppack.nv
  unpack PACKAGE -o IMAGE   takes the NOVB image out of a package

`--tcp` and `--serial` carry the console framing of SMP over a socket and over a serial port, which
the program puts in raw mode at `--baud` (115200 when absent).  `--dev` is a descriptor used as it is,
such as a pty already in raw mode.  `--pipe` starts PROGRAM and talks to it in raw packets through its
standard input and output: the relay of noble-examples that reaches a device over Bluetooth Low Energy.
`run` answers the exit
status: 0 for success, 1 for a code the server answered or a file that
could not be read or written, 2 for a usage error and 3 when no answer
came.

## Module `smpclient` {#module-smpclient}

smpclient: the commands of the `smp-client-nv` program, which print what smpapi.nv returns.

Each command sends its request through a `Transport` (smptransport.nv) and prints what the response holds: the images, the
length of a file, the CRC-32 of one.  A request that is not answered within the timeout is sent again, up to `tries` times; a
response that does not belong to the request, by its sequence number, is ignored.  The logic is smpapi.nv's, and a program that
wants the values and not the lines calls that module.

Every command answers a code: 0 for success, the server's code for a request it refused, and a negative number when the
command did not come to an answer (the `E_` codes of smpapi.nv; -1 when no response arrived).

## Module `smpdevice` {#module-smpdevice}

smpdevice: a simulated device for the suites of a program that speaks SMP, and a Central that reaches it.

The device is the server of mcumgr-nv over RAM slots with novoboot's start-up rule: a request goes to the real session, a reset request
swaps the slots as the bootloader does, and an image that runs on trial and is not confirmed before the next start is reverted.  It keeps
the slots, counts the starts, and has the faults a suite asks for: the candidate image hangs (the watchdog restarts the device before
anything can confirm it), the device ignores a reset request, and the device is off the air for some attempts to reach it after a start.

`Periph` is a `GattCentral` that wraps the scripted double of ble-central-nv and answers a write to the SMP characteristic with the
notifications of the device's response.  The pieces of a response can be set, lost, doubled and held back, and the link can be cut.
`smpdirect.nv` reaches the same device as a `Transport` with no radio model between.

The device is module state: one device per process, made by `fresh`.

## Module `smpgatt` {#module-smpgatt}

smpgatt: the SMP transport over the GATT operations of a Central.

A device that runs the SMP service of MCUmgr over Bluetooth Low Energy has one service and one characteristic.  A request is written to
the characteristic without a response, and the response comes back as notifications.  A packet longer than one write or one notification is
cut with no added framing, GATT keeps the order, and the Data Length in the header of the first piece says where the packet ends.

`GattLink` implements `Transport` over any `GattCentral` of ble-central-nv: the noble Host on a PC, the Bluetooth API of a phone, or the
scripted double of a test.  The package knows no radio; the Central is the program's.

  match smpgatt.open(central, peer, smpgatt.options())
      Err(e)   => println(e.message())
      Ok(link) => println(smpapi.image_list(link, smpapi.options(10000, 3)).is_ok())

`open` connects, discovers the service, asks for the largest MTU, asks for the short connection interval, and subscribes.  `send` writes a
packet in pieces of `max_write` bytes, each waited for, and first forgets what a response before it left behind: the notifications that are
waiting and the pieces of a packet that never ended.  `recv` joins the pieces of one response by the length in its header and answers it
whole.  It answers None when no piece arrives within the time, and then forgets the pieces it held; it also answers None when the link has
ended.  A command of smpapi.nv that gets None sends its request again, up to its tries, so a piece that was lost costs one request.

A link that ended is `lost()`.  The commands of smpapi.nv answer `E_SEND` or `E_NO_ANSWER` for it, which a device that does not answer
gives too, so a caller that must tell the two apart asks the link.  `reopen` connects the same peer again on a new link of the same value;
an upload that was cut resumes from the offset the device kept (smpapi.nv, `image_upload_to`).

What the pieces of a response may look like: a header that is cut over several pieces, a piece that holds the end of one packet and the
start of the next, a piece that was lost and one that arrived twice.  A run of bytes whose first eight bytes cannot be the header of a
response (reserved bits set, a version the protocol does not define, an operation that is a request) is dropped a byte at a time until
a header is found, so a stray tail of an earlier response does not hold up the next.  A piece that arrived twice, or one that was lost and
whose gap the next response closed, gives a packet whose body is not whole, which smpapi.nv passes over and asks again.

## Module `smpscript` {#module-smpscript}

smpscript: a Transport whose far end is a script.

A program that speaks SMP through a `Transport` tests its error paths against a `Scripted` one: the test queues the packets the
device would send, in order, and reads back the packets the program sent.  Nothing is opened and no time passes, so a lost
answer, a late answer, an answer for another request, a cut packet and a link that refuses a write are lines of a test.

  let dev = smpscript.scripted()
  dev.answer(canned_image_list)      // the next `recv` after a `send` delivers this packet
  dev.silence()                      // the one after it times out
  dev.answer_raw(stale_packet)       // delivered as it is, with the sequence number it has
  let r = smpapi.image_list(dev, smpapi.options(100, 2))

An answer queued with `answer` takes the sequence number of the request sent last, which a canned packet cannot know: the client
numbers its requests and ignores an answer whose number is another.  `answer_raw` keeps the packet as it is.  A `recv` with no
step left times out.  The packets are `Bytes`; `packet_of` makes one from a buffer a test filled with the builders of mcumgr-nv.

## Module `smptransport` {#module-smptransport}

smptransport: how an SMP packet reaches a server from a host.

A `Transport` sends one packet, an SMP header and its body, and receives
one.  What differs between the ways to reach a server is how the packet is
carried, and the package has two:

  Framed   the console framing of the serial transport (smpserial.nv):
           base64 lines with a length and a CRC-16.  A serial port, a pty
           and a TCP socket carry it; so does the host server of
           mcumgr-nv.
  Raw      the packet as it is, one after the other.  A reader finds the
           end of a packet in its header, whose bytes 2 and 3 hold the
           length of the body.  A pipe to a relay carries it; the relay of
           noble-examples (its program ble_smp) is the one that puts the packets
           on the SMP service of a device over Bluetooth Low Energy.

Both are written over a `Wire`, the bytes of a host: `TcpWire` for a
socket, `DevWire` for a descriptor such as a serial port and `PipeWire` for
the two ends of a child process.  A program that has another way to carry
bytes implements `Wire`; one that has another way to carry packets
implements `Transport`.

A `recv` that gets no byte within `ms` milliseconds, or whose peer has
closed, answers `None`.

buffer of the package's configuration, whichever is smaller.  A transport whose state changes with a packet keeps it in a field

## Module `update` {#module-update}

update: `novo update`, the command that updates a board over SMP.

  novo update [--target BOARD] [LINK] [OPTIONS] FILE
  novo update [--target BOARD] [LINK] [OPTIONS] VERB [ARGUMENTS]
  novo update scan [--target BOARD] [--serial | --ble]

LINK says how the board is reached:

  --serial [PORT]   the board's serial port, in the console framing of SMP.  Without a PORT the
                    serial ports of attached USB boards are listed, and the one there is, is used.
  --ble [ADDRESS]   the SMP service of a device over Bluetooth Low Energy, through a relay
                    program that has a Controller (the program `ble_smp` of noble-examples).  Without an
                    ADDRESS the relay scans for devices that advertise the service, the devices
                    are listed, and the one there is, is used.
  --tcp HOST:PORT   a server on a socket, such as mcumgr-nv's host server.

A FILE alone is an upload to the second slot: a NOVB image (`novo build --role=application`
writes `<name>.img`) or the package `novo image pack` writes.  The VERBs:

  upload FILE       the same, said out
  data FILE         the file `novofs-tools mk --target` wrote, into the data region (image 1)
  list              the images the board holds
  test HASH         marks the image with the hash (hex) for a trial at the next start
  confirm [HASH]    confirms the image that runs, or makes the staged one permanent
  reset             the board restarts
  erase             erases the second slot
  params, echo TEXT what the server answers about itself; a check of the link
  file up LOCAL NAME | file down NAME LOCAL | file status NAME | file hash NAME | file close
                    the files of the board's volume, as far as the server offers them

With a FILE or `upload`, --test marks the new image for a trial and resets the board, and --confirm
waits for the board to answer again and confirms the image that runs; --confirm alone makes the
staged image permanent and resets.  --baud N (115200), --timeout MS (10000), --tries N (3) and
--wait SECONDS (120, how long to wait for the board after a reset: the swap of a 340 KB image takes 63 s on the nRF54LM20-DK) are the other options.

The board's [flash] table is read from the toolchain (`novo bsp flash --target BOARD --json`), so
that this program does not parse the manifest: it tells the size of slot B and of the data region
and the vendor id of the board's probe, which names its serial port.  The exit status is 0 for
success, 1 for a code the server answered, 2 for a usage error, 3 when the board could not be
reached or gave no answer.
